滑动窗口统计：原理与动态过程

dem_buck · env/buck_win_stats.sv 的可视化对照版 · 配套文档 令牌桶与滑窗统计.html

本页把滑窗统计的每一步做成动画：窗口如何滑、峰值如何被刷新、多档窗口如何联立出 R 与 B。每个演示都标出它对应 buck_win_stats.sv 的哪一段代码。

术语约定。W = 窗口宽度；peak(W) = 所有位置的 W 宽窗口里字节数的最大值；depth = 取到峰值时窗口内的包数。本页时间单位统一用 us，字节用 byte。时间戳取包的末 beat，即整包字节记在它传输完成的瞬间。

1. 窗口在滑动：半开区间 (t−W, t]

一个固定宽度 W 的窗口，右端点钉在「最新到达的那个包」上。每来一个包，就把它压进队尾、加进 sum，再把左端滑出去的包逐个弹掉、从 sum 里减掉。

窗口内的包（计入 sum） 已滑出窗口 当前窗口 (t−W, t] 历史峰值
窗口内 sum0
窗口内包数 depth0
peak(W)0
峰值处 depth0
队列长度0

注意看日志里的弹出动作：队列只在左端弹、只在右端压，sum 是增量维护的，从不重新遍历。每个包一生只被压入一次、弹出一次，所以均摊下来每次 add() 是 O(1)，跟窗口里装了多少包无关。

// sliding_window::add() —— 这段就是上面的动画
lo = t_ns - width_ns;
t_q.push_back(t_ns);  b_q.push_back(nbytes);  sum += nbytes;
while (t_q.size() > 0 && t_q[0] <= lo) begin      // 半开区间故用 <=
    sum -= b_q[0];  void'(t_q.pop_front());  void'(b_q.pop_front());
end
if (sum > peak_bytes) begin
    peak_bytes = sum;  peak_end_ns = t_ns;  peak_depth = t_q.size();
end

为什么是半开区间 (t−W, t]。弹出条件写 t_q[0] <= lo 而不是 <，意味着恰好落在左端点 t−W 上的包算滑出。这样任意两个相距正好 W 的包不会被同一个窗口同时装下，窗口「宽度」才名副其实。若用闭区间，宽 W 的窗口实际能覆盖 W 加一个时刻点，峰值会系统性偏大。

2. 为什么峰值只会落在到达时刻

窗口可以放在时间轴的任意位置，位置是连续的、无穷多个。但组件只在包到达的那些离散时刻检查了峰值 —— 这样会不会漏掉真正的最大值？

自由平移的窗口 被窗口覆盖的包 右端点贴在到达时刻
当前窗口字节0
平移过程最大值0
只查到达时刻的最大值0
两者是否相等—

把窗口从左扫到右，下方折线是窗口内字节数随位置的变化。它是阶梯状的：窗口右端点越过一个包时整包跳上去一级，左端点越过一个包时整包掉下来一级。

结论：峰值必然在某个「右端点恰好压住一个到达时刻」的位置取到。理由是把窗口向右平移一点点，只有两种后果 —— 要么没跨过任何包，字节数不变；要么左端点先滑掉一个包，字节数下降。所以从任意位置出发向右推到「右端点撞上下一个到达时刻」为止，字节数只增不减。连续的无穷多个位置，因此被压缩成有限个到达时刻，这就是只需在 add() 里检查峰值的全部依据。

这个性质依赖「字节在离散时刻整包记账」这一建模。buck_win_stats 取包的末 beat 时刻，所以一个包的字节全部算在它传完的瞬间 —— 包在总线上传输的那段时间里，字节并非均匀地流进窗口。这正是后面 §6 要裁掉 depth <= 1 那些行的原因。

3. 固定窗口均值 vs 滑窗峰值

monitor 的 measured_Bps() 只给「首包到末包」这一个固定窗口的平均值。下面把同一条包流同时喂给两种口径，看它们各自测到什么。

把开场突发拉大：全程平均几乎不动（分母是整个仿真跨度，一次突发摊薄了），但滑窗峰值立刻抬高。平均值回答「总共发了多快」，滑窗峰值回答「最密的那一瞬间有多密」 —— 后者才是整形器要卡的东西。

反过来，平均值也有它不可替代的地方：滑窗峰值不受「自愿 idle」影响，一段长时间不发包不会把峰值拉低。所以两个口径互为补充，组件不在这里重算平均，需要平均值时看 monitor。

4. 多档窗口同时跑

单一个 W 只能给出一个数 peak(W)。而契约 cost(T) ≤ R·T + B 有两个未知数，一个方程解不出来。所以组件在一次仿真里并行维护多个宽度的窗口，每来一个包就挨个喂进去。

窗口内字节 该档历史峰值 窗口剩余容量
当前时刻0 us
已记包数0
采样跨度0 us

每一行是一个独立的 sliding_window 实例，共用同一串 add() 调用。观察两件事：

  • 窄窗口很快就「满」了 —— 它的峰值早早定格，因为它装不下更多包，再长的仿真也抬不高它。
  • 宽窗口的峰值一直在涨 —— 它还在不断装进新包，直到窗口宽度超过整个采样跨度为止。
peak(W) ≈ R · W + B
窄窗：B 占主导（突发信用）　宽窗：R·W 占主导（持续速率）

这就是为什么多档窗口能分离 R 和 B：窄端的点主要由桶深撑起来，宽端的点主要由速率撑起来，两端一起上才能把截距和斜率同时定下来。

5. peak(W) 曲线与那条直线

§4 跑完一遍，手里就有一组点 (W₁, peak₁), (W₂, peak₂), …。契约说这些点该落在一条直线上：斜率是 R，截距是 B。于是「反推配置」就变成了一道最小二乘拟合题。

看三件事：

  • 刚开跑时点全趴在低位，拟合线乱飘 —— 样本还不够，每档窗口都没碰上它这辈子最挤的那一刻。
  • 包越来越多，各档峰值逐个「顶住」，点列慢慢贴上灰色理论线，fit_R / fit_B 随之收敛。
  • 峰值只增不减，所以每个点只会往上爬。这意味着仿真时间不够时，结果一定偏小，不会偏大 —— 误差方向是可预期的。
// fit_line(): 对各档 (W, peak) 做最小二乘
den   = n * sxx - sx * sx;
fit_R = (n * sxy - sx * sy) / den;      // 斜率 → 速率 R
fit_B = (sy - fit_R * sx) / n;          // 截距 → 桶深 B

为什么截距就是桶深。把直线外推回 W = 0，问的是「时间宽度趋近于零时还能挤出多少字节」—— 那正是桶里预存的信用 B。所以窄端的点决定截距准不准：窄端太疏，外推出来的 B 方差就大。

6. 两道过滤：哪些点不能要

不是每个 (W, peak) 都能进拟合。有两类点天生不在那条直线上，混进来会把斜率和截距一起带偏，fit_line() 开头两行就是把它们挡在门外。

foreach (win[i]) begin
    if (win[i].peak_depth <= 1)      continue;   // 装不下两个包
    if (win[i].width() > span_ns)    continue;   // 比采样跨度还宽
    ...
end

把两个勾去掉，看误差怎么炸：

  • peak_depth ≤ 1 —— 窗口太窄，连两个包都装不下，peak 恒等于单包字节数，跟 W 没有关系。这些点在图上是一排贴地的水平点，它们反映的是总线粒度而不是令牌桶，会把截距硬往下拽。
  • W > span —— 窗口比整段采样还宽，窗口里永远装着全部包，peak 饱和成一个常数。这些点在图上是一排贴顶的水平点，把斜率往下压。

拖动「采样包数」能看到第二道过滤的动态含义：span 在涨，合格的宽窗口就一档一档被解锁。所以宽端档位不是白设的，只是要等仿真跑够长它才开始说话。

两道过滤后若剩不到两个点，斜率与截距无法分离，fit_line() 直接把 fit_n 置 0 放弃拟合。看到报告里 fit_n = 0，先查是不是仿真太短或档位设得离谱，而不是怀疑 DUT。

7. 等比 vs 等差：档位怎么排

档位区间默认是 10us ~ 10000us，横跨三个数量级。在这样的区间里，等比和等差不是风格差异，是能用与不能用的差异。

等比档位 等差档位 拐点 W* = B/R 被过滤掉的档
拐点 B/R–
等比 fit_R / 点数–
等比 R 误差–
等差 fit_R / 点数–
等差 R 误差–

横轴是对数刻度。等比档位在对数轴上等间距铺开，等差档位则全部挤在右端 —— 区间 [10, 10000] 的等差步长是 (10000 − 10) / 7 ≈ 1427us，于是档位是 10 / 1437 / 2864 / … / 10000：第一档和第二档之间空了 1427us 的无人区。

而拐点 W* = B/R 正落在这片无人区里（拖 B 滑块看紫线怎么走）。拐点以左的点才带桶深信息，可等差在那一侧只剩 10us 一个孤点，还经常因为 peak_depth ≤ 1 被过滤掉 —— 截距就彻底没人支撑了。

闭环论证。等差要成立，必须把区间收窄到一个数量级以内；可收窄的前提是事先知道拐点在哪，而拐点 = B/R 恰恰就是待拟合的那两个未知数。拟合的前提是 R、B 未知；既然未知，就没有依据去挑那个窄区间；挑不了窄区间，就只能跨量级；跨了量级，就只能等比。

所以 win_log 是兼容开关，不是调优旋钮。常规验证一律用默认等比，不要按 case 去切。要在某个可疑宽度附近做局部精查，请直接给 win_us 显式列表（它一给，win_min_us / win_max_us / win_num / win_log 四项全部被忽略）。详见手册 §8.3。
