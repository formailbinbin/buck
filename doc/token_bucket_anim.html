本页把令牌桶的每个机制做成可操作的动画：拖动参数、单步执行、观察内部状态变化。每个演示下面都标出它对应 token_bucket.sv 的哪一段代码。

术语约定。R = 令牌注入速率（token/s）；B = 桶深（token）；cost = 单包开销；TAT = 理论到达时间。本页时间单位统一用 ms，令牌单位用 byte，便于读数。

1. 桶的运行：注入与取用

令牌以速率 R 持续注入一个容量为 B 的桶，溢出部分丢弃。每个包发送前取走 cost 个令牌，不够就等到够。

当前令牌—
放行包数0
累计开销0
实测速率—
累计 stall0.0 ms

把到达间隔调小（请求变密），桶很快被抽干，此后每个包都要 stall，实测速率收敛到 R；把间隔调大到让平均请求速率低于 R，桶长期是满的，没有包需要等 —— 此时桶不是瓶颈，实测速率由到达速率决定。这就是那条关键性质：

实际速率 = min(令牌桶上界 R, 请求到达速率)

令牌桶是上界整形器，不是节拍器。契约 cost(T) ≤ R·T + B 是单侧不等式，只规定「不许更快」，不规定「必须这么快」。所以自愿 idle 不算违约，但也意味着：想用桶把速率卡在 R，必须保证请求足够密。

2. 速率与桶深各管什么

R 管长期平均带宽，B 管瞬时突发量 —— 两个旋钮互不干扰。下图是「累计放行量 vs 时间」，斜率就是速率。

当前段斜率—
raw 平均—
raw 误差—
理论 B/(R·T)—

曲线永不越过绿线（上界 R·t + B），这就是符合性。开场那段陡坡是桶里的存货被一次放出，长度正是 B；之后斜率贴合 R。把「初始令牌」拉到 0，陡坡消失，曲线从一开始就贴着基准线走 —— 这正是 tc_buck_base 设 init_tokens=0 的用意。

注意 raw 误差 与 理论 B/(R·T) 两个读数始终贴近。这解释了为什么 tc_buck_burst（B=8192）在短窗口下 raw 误差高达 41% 却完全正常 —— 它衡量的是桶深占比，不是整形精度。

桶深的时间尺度是 B/R。它表示「攒多久的额度能一次性放出去」。例如 R=2 MB/s、B=8192 B 时 B/R = 4.1 ms。想让 raw 可信，窗口须满足 T ≫ B/R。

3. 两种实现：令牌计数 vs 虚拟时间

同一个算法有两种写法。左边是直观的「维护 tokens 变量 + 循环等待」，右边是本项目采用的 GCRA 虚拟时间。点单步，看两边的内部状态如何演进。

左：tokens 变量—
左：累计循环次数0
右：TAT − now—
两者令牌差0.000

两者的等价关系是一个恒等式 —— 右侧读数 TAT − now 乘以 R 再被 B 减去，恰好等于左侧的 tokens：

tokens(t) = B − (TAT − t) · R

于是「令牌足够」的判据可以改写成纯时间比较，最早放行时刻一次闭式算出：

tokens ≥ cost  ⟺  t ≥ TAT − (B − cost)/R
方面令牌计数 + 循环等待GCRA 虚拟时间
等待时间while 逐次逼近，上面计数器会涨一次求解，无循环
浮点误差反复累加 + 上限裁剪，会漂移TAT 只按精确 cost/R 递增
边界兜底需防零延时死循环不需要
仿真开销每包可能多次唤醒每包最多一次 #delay
后台线程常需 forever 补令牌惰性计算，空闲零开销

4. TAT 推进：四行代码逐步拆解

这是 consume() 的核心临界区。下面把每个包的处理拆成 4 步，逐步高亮并同步更新时间轴。

sem.get(1);
t_ns        = real'($realtime);
earliest_ns = tat_ns - tok2ns(cfg.bucket_size - need);
start_ns    = (earliest_ns > t_ns) ? earliest_ns : t_ns;
tat_ns      = ((start_ns > tat_ns) ? start_ns : tat_ns) + tok2ns(need);
sem.put(1);
① t_ns = $realtime 读当前时刻
② earliest_ns = tat_ns - (B - need)/R 令牌够了的最早时刻
③ start_ns = max(earliest_ns, t_ns) 实际放行时刻
④ tat_ns = max(start_ns, tat_ns) + need/R 预约时隙, 扣未来额度

两层 max 分别防什么

位置作用去掉会怎样
③ max(earliest_ns, t_ns)令牌已够时取当前时刻，立即放行earliest 可能是过去时刻，算出负延时
④ max(start_ns, tat_ns)空闲期不让 TAT 落后于现在长时间空闲后 TAT 远在过去，桶会「攒出」远超 B 的额度，突发上限失守

把「距上包」拉到最大（长时间空闲）再单步，可以看到 ④ 的内层 max 生效：tat_ns 被抬到 start_ns，而不是从那个早已过期的旧值继续累加。这正是「桶满即溢出」在虚拟时间下的等价表达。

这四行不消耗仿真时间，所以临界区是真正的 O(1)。等待 #delay 放在 sem.put() 之后执行 —— 若在持锁期间等待，一条流等令牌就会锁住整个桶，造成队头阻塞（见第 8 节）。

5. 超桶深的包：截断为什么是错的

当 cost > B，一种常见的「顺手」写法是把开销截断成 B 再计费。下面并排跑两个桶，输入完全相同，只有计费方式不同。

截断：实测速率—
截断：误差—
实际：实测速率—
实际：误差—
截断少收费合计0

红线斜率持续高于基准线：每个大包都被打了折，少收的那部分永久性地变成了超额带宽，长期速率高于配置值 —— 整形器失守。把「大包比例」拉高，偏差线性放大。

本项目按实际开销计费，不做截断。GCRA 下这天然成立：cost 越大，TAT 被推得越远，该包自己承担更长等待，速率自动摊平。effective_cost() 只发一条 warning 而不改数值：

if (cost > cfg.bucket_size) begin
    if (cfg.allow_oversize)
        `uvm_warning("TB_OVERSIZE", ...)   // 放行, 但按实际开销计费
    else
        `uvm_fatal("TB_OVERSIZE", ...)
end
return cost;                               // 关键: 返回原值

代价是这个包会短暂「借支未来额度」，所以 current_tokens() 允许返回负值 —— 它正确反映了欠账状态。桶只裁上限、不裁下限：

tok = cfg.bucket_size - (tat_ns - $realtime) * R / 1e9;
return (tok > cfg.bucket_size) ? cfg.bucket_size : tok;   // 只裁上限

6. 符合性：为什么必须覆盖任意窗口

契约要求 cost ≤ R·T + B 对任意窗口成立。下面的曲线是 f(t) = cost(t) − R·t，它把「超额」这件事画成了一张图：任意窗口的超额就是 f 在该区间的涨幅。

f(t) = cost(t) − R·t running 最小值 f_min 当前最大超额区间
f(t)—
f_min—
max_excess—
只看首包起点—
conformant—

选「含中途空闲」可以看到两个读数分道扬镳：空闲期 f 被持续压低，f_min 跟着下探；随后一轮突发让 f 抬升，真实超额是这一段的涨幅。而「只看首包起点」的朴素算法完全漏掉了它。

任意窗口最大超额 = maxt [ f(t) − minτ≤t f(τ) ]

所以只要维护 f 的 running 最小值，一次比较就能覆盖所有窗口，不必存历史，代价 O(1)：

f_before = total_cost - span_s * rate;
if (f_before < f_min) f_min = f_before;      // 先更新 running 最小值

total_cost += add_cost;

f_after = total_cost - span_s * rate;
if ((f_after - f_min) > max_excess)
    max_excess = f_after - f_min;             // 报告里的 burst used

加 cost 前后各算一次 f，顺序不能颠倒。加之前的值用于更新 f_min（窗口左端取在本包之前），加之后的值用于更新 max_excess（右端取在本包之后）。颠倒会让同一个包既算进左端又算进右端，低估超额。

把「额外总线延时」从 0 拉到 80%：raw 和 steady 双双下滑，而 conformant 稳稳是 YES。

两个 rate 函数的分母是墙钟时间，分不清「等令牌」与「等总线」。它们看到的只是「两次放行之间隔了多久」，无法区分这段时间是桶在限速还是下游在堵。所以判整形器对不对，先看 conformant 与 steady，再看 raw，且必须确认 T ≫ B/R。

「稳态起点」的判据很干净：首次 stall。桶里还有存货时不会 stall，一旦 stall 说明存货已空，此后系统完全由 R 支配。

if (stalled && !steady_valid) begin
    steady_valid      = 1;
    steady_start_time = $realtime;
    steady_start_cost = total_cost;
    steady_start_cnt  = grant_cnt;
end

8. 多流共享一个桶

两条 sequence 共用一个桶时，总流量应受限于 R。关键在于临界区怎么写 —— 下面对比「锁内等待」与「锁外等待」。

流 B 吞吐—
合计吞吐—

两种模式下合计吞吐都收敛到 R —— 总速率受限这一点不受影响。差别在公平性与仿真行为：锁内等待时，一条流在 #delay 期间霸占着锁，另一条流连「预约时隙」都做不到，红色的等锁条会堆积起来。

sem.get(1);
  // 纯运算: 算 start_ns, 推进 tat_ns —— 不消耗仿真时间
sem.put(1);

delay_ns = start_ns - t_ns;
if (delay_ns > 0.0) #(delay_ns * 1ns);   // 等待放在锁外

SV semaphore 的唤醒顺序并非 LRM 保证的 FIFO，这也是把临界区压到 O(1) 的另一个理由：锁的持有时间趋于零，请求实际按到达顺序拿到时隙。

9. 包内空隙与瓶颈转移

一个包由多个 beat 组成。beat_gap() 允许在 beat 之间插空闲拍 —— 这会改变什么？下面的时序图把一个包的微观节奏画出来。

valid && ready（有效 beat） 包内空隙（valid 拉低） DUT FIFO 水位 背压（ready 拉低）
有效 beat 数0
搬运字节0
总线占空比—
FIFO 峰值0 / 16
背压拍数0

插隙概率设 0 时输入背靠背（4 B/2 ns = 2e9 B/s），DUT 排空速率是 4 B/4 ns = 1e9 B/s，恰为线速一半，于是 FIFO 被填满并触发背压。把概率拉到 100%、空隙拍数拉大，输入降到排空速率以下 —— FIFO 峰值与背压拍数双双归零。

这就是「不要让每个 beat 都插空隙」的原因。背压路径与 driver 等 ready 的分支会双双失去覆盖。所以空隙必须随机、并保留相当比例的 0，让背靠背片段与空隙片段混合出现 —— buck_gap_driver 默认 gap_percent=40 正是这个意思。

各层的受影响情况

层次受影响原因
monitor / DUT 计数否二者只在 valid && ready 成立时动作，空闲拍被天然忽略
is_conformant()否不依赖窗口口径
raw / steady小空隙可忽略线速远高于 R，裕量很大；超出后 driver 成瓶颈，两项都偏低
背压 / FIFO 覆盖是见上

空隙只能插在握手完成之后。valid 一旦拉高，在 ready 到来前不得回撤 —— 这是 valid/ready 协议的硬性要求。所以实现上必须等 do...while(ready !== 1) 退出后再拉低 valid。

回归实测（tc_buck_beatgap vs tc_buck_base，同配置）印证了上表：beat/byte 逐位相同（7106 / 28137），仿真时长仅 +3.8%，conformant 都是 YES。

10. 速查

现象先看哪个常见原因
raw 误差很大但 steady 准window 与 B/R 的比值窗口太短，桶深占比被当成了误差
raw 与 steady 双双偏低是否有背压 / 包内空隙瓶颈已转移到总线或下游，不是桶
conformant = NOburst used 超了多少真正的整形失守：截断计费、TAT 回退、桶深配置不符
长期速率高于配置值有无 oversize 包被截断大包打折，见第 5 节
多流合计超过 R临界区是否原子时隙预约未加锁，两条流拿到重叠时隙
背压路径没覆盖插隙概率输入速率降到 DUT 排空速率以下，见第 9 节

一句话版。conformant 是唯一在任何情形下都严格成立的硬判据；steady 判整形逻辑；raw 判带宽达标但必须先确认窗口足够长。
