第 一 部 分

令牌桶产生激励

按 R / B 整形发包 —— 原理、GCRA 实现、易错点、自检与源码

1. 它解决什么问题

验证环境里经常需要「按指定速率发包」：构造背压、复现带宽瓶颈、测下游 FIFO 水位。朴素做法是在 sequence 里插固定延时，但这样做有两个缺陷：无法表达突发行为，且包长变化时实际带宽会漂移。

本 demo 用令牌桶（token bucket）做流量整形，提供两个可独立配置的旋钮：

  • 速率 R — 控制长期平均带宽
  • 桶深 B — 控制允许的瞬时突发量

计费单位由调用方决定：item_cost() 返回包长则 R 的单位是 byte/s，返回 1.0 则单位是 packet/s。同一套代码既能控带宽也能控包率。

2. 令牌桶原理

设想一个容量为 B 的桶，令牌以恒定速率 R 注入，溢出部分丢弃。每个包发送前须取走 cost 个令牌；不足则等待。

R token/s │ ▼ ┌───────────┐ │ ░░░░░░░░░ │ ← 桶深 B（溢出即弃） │ ░░░░░░░░░ │ └─────┬─────┘ │ 取 cost 个令牌 ▼ ┌───────────┐ │ 发包 │ 令牌不足 → 等待 └───────────┘

由此得到两条性质，也是令牌桶的全部契约：

任意窗口 T 内的放行量：  cost(T) ≤ R·T + B
  • 长期平均速率收敛到 R。B 是一次性常数，T→∞ 时 B/T→0。
  • 瞬时突发上限为 B。桶满时可一次性放行 B 个令牌的流量，这是特性而非缺陷。

桶深怎么选。B 决定了「攒多久的额度能一次放出去」，时间尺度是 B/R。例如 R=2 MB/s、B=8192 B，则 B/R = 4.1 ms —— 意味着约 4 ms 的额度可以瞬间释放。想测稳态就把 B 设小、init_tokens=0；想压下游缓存就把 B 设大。

3. 实现：为什么用虚拟时间而非令牌计数

直观实现是维护一个 tokens 变量，按经过时间累加、按开销扣减，不足时循环等待。本 demo 不这样做，而是维护 TAT（Theoretical Arrival Time，理论到达时间），即 GCRA（Generic Cell Rate Algorithm）。两者严格等价：

tokens(t) = B − (TAT − t) · R

3.1 这个恒等式是怎么来的

先说直觉。TAT 的物理含义是「桶恢复到满（tokens = B）的那个时刻」。既然从 t 起还要再等 TAT − t 才攒满，而这段时间能攒 (TAT − t)·R 个令牌，那说明此刻距离满还差 (TAT − t)·R —— 当前库存就是 B 减掉这个缺口。

再说严格推导。令牌桶的原生递推是：

tokens(t + Δ) = min(B, tokens(t) + R·Δ)

先把 min 摘掉。那么 tokens 就是时间的一次函数，斜率恒为 R。一次函数只要给定「一个锚点 + 斜率」就被唯一确定 —— GCRA 的技巧就在这里：不存库存值，而是存那个锚点的横坐标。挑 tokens = B 的时刻作为锚点，记作 TAT，于是

tokens(t) = B + R·(t − TAT) = B − (TAT − t)·R

然后把 min 装回来。min(B, ...) 的截断，在虚拟时间里等价于「TAT 跑到了当前时刻之前」：

TAT < t  ⟺  B − (TAT − t)·R > B  ⟺  桶已满并开始溢出

所以 current_tokens() 里只需要裁上限那一行，就完整复刻了原生递推里的 min：

tok = cfg.bucket_size - (tat_ns - $realtime) * R / 1e9;
return (tok > cfg.bucket_size) ? cfg.bucket_size : tok;   // 只裁上限

3.2 为什么放行之后恒等式仍然成立

初值由 configure() 直接按定义反折，恒等式天然成立：

tat_ns = real'($realtime) + tok2ns(cfg.bucket_size - init_tok);
//       即 TAT - t = (B - tokens) / R

归纳步要证的是「放行后的新库存 = 放行时刻的库存 − cost」。consume() 的推进式是 TAT_new = max(start, TAT_old) + cost/R，分两种情况：

情况含义TAT_new代入恒等式
start ≥ TAT_old空闲太久，桶早已满，真实库存被上限截断为 Bstart + cost/RB − cost = tokens(start) − cost ✓
start < TAT_old桶未满，库存由 TAT 精确给出TAT_old + cost/RB − (TAT_old − start)·R − cost = tokens(start) − cost ✓

两种情况都保持不变量，所以恒等式在整条放行序列上永远成立。

推进式里那个内层 max 对应的正是第一种情况。不加它，TAT 会停在过去，等价于让桶攒出超过 B 的额度 —— 也就是「桶满不溢出」的 bug。它是「桶满即溢出」在虚拟时间下的等价表达。

3.3 三个直接推论

一、放行判据变成闭式解。把恒等式代进 tokens ≥ cost：

tokens ≥ cost  ⟺  B − (TAT − t)·R ≥ cost  ⟺  t ≥ TAT − (B − cost)/R

右侧即该包的最早放行时刻 earliest_ns，一步算出，不需要任何循环。核心代码只有四行：

t_ns        = real'($realtime);
earliest_ns = tat_ns - tok2ns(cfg.bucket_size - need);
start_ns    = (earliest_ns > t_ns) ? earliest_ns : t_ns;
tat_ns      = ((start_ns > tat_ns) ? start_ns : tat_ns) + tok2ns(need);

二、库存允许为负。当 TAT − t > B/R 时恒等式给出负值，这正是 oversize 包「借支未来额度」的状态，所以不能裁下限（见 4.1）。

三、浮点不漂移。库存从来没被反复累加，每次都从 TAT 一次算出；而 TAT 自己只做单调加法。

3.4 与令牌计数法的对比

相比令牌计数法的收益：

方面令牌计数 + 循环等待GCRA 虚拟时间
等待时间计算while 循环逐次逼近一次闭式求解，无循环
浮点误差反复累加 + 上限裁剪，会漂移TAT 只按精确 cost/R 递增
边界兜底需 if (wait < 0.001) 防零延时死循环不需要
仿真开销每包可能多次唤醒每包最多一次 #delay

另外全程不起后台 forever 线程 —— 令牌是「按需惰性计算」的，空闲时零仿真开销。

4. 三个易错点与对应设计

4.1 超桶深的包不能截断计费

当 cost > B 时，若把开销截断为 B 再计费，大包就会少收费，长期速率会高于配置值 —— 整形器失守。

本实现按实际开销计费，不做截断。GCRA 下这天然成立：cost 越大，TAT 推得越远，该包自己承担更长等待，速率自动摊平。allow_oversize=0 时则报 fatal。

4.2 符合性检查必须覆盖任意窗口

契约要求 cost ≤ R·T + B 对任意窗口成立。若只以首包时刻为起点检查一个窗口，会漏掉「中途空闲、随后突发」的情况。

令 f(t) = cost(t) − R·t，则任意窗口的超额为 f(t₂) − f(t₁)，其最大值是 f(t) − min(f)。因此需跟踪 f 的 running 最小值，代价是 O(1)：

f_before = total_cost - span_s * rate;
if (f_before < f_min) f_min = f_before;      // running 最小值

total_cost += add_cost;

f_after = total_cost - span_s * rate;
if ((f_after - f_min) > max_excess)
    max_excess = f_after - f_min;             // 实际用掉的突发信用

报告里的 burst used 就是这个 max_excess，它必须 ≤ 桶深。

4.3 等待不能持锁

多条 sequence 共享一个桶时需用 semaphore 串行化，但若在持锁期间执行 #delay，一条流等令牌会锁住整个桶，造成队头阻塞。而且 SV semaphore 的唤醒顺序并非 LRM 保证的 FIFO。

解法是把临界区压到 O(1)：锁内原子预约时隙，锁外等待。

sem.get(1);
  // ... 计算 start_ns, 推进 tat_ns（纯运算，不消耗仿真时间）
sem.put(1);

delay_ns = start_ns - t_ns;
if (delay_ns > 0.0) #(delay_ns * 1ns);   // 锁外等待

总速率不受影响，且请求按到达顺序拿到时隙 —— 真正的 FIFO 整形。

5. 桶的自检：raw、steady 与符合性

这是最容易产生误解的部分。桶自己的报告同时给出三个指标，各自回答不同问题 —— 注意这三项的数据源都是桶的内部状态，与第二部分的滑窗统计无关。

指标含义回答什么问题
measured (raw)全窗口平均，含开场突发长期带宽占用是否达标（SLA 口径）
steady首次 stall 之后的平均整形器的令牌发放逻辑是否准确
conformantburst used ≤ B是否违反 cost ≤ R·T + B

5.1 raw 误差为何可能很大

短窗口下 raw 误差约等于 B / (R·T)。桶深越大、窗口越短，这个值越大 —— 它衡量的是桶深占比，不是整形精度。

精简版保留了什么

有两处看似「可以再砍」的代码被刻意留下：

一、构造时的参数校验。rate <= 0 会让 tok2ns() 除零，bucket <= 0 会让每个包都 stall 满额 —— 这两个错误如果不在构造时 fatal，表现出来是难以定位的仿真挂死，而不是报错。

二、cost <= 0 直接 return。完整版靠 effective_cost() 挡住，精简版里这是唯一必须保留的防御：

// 负 cost 会把 tat 往回拨, 破坏单调性
if (cost <= 0.0) return;

这不是「给不可能的场景加校验」，而是状态机不变量的守卫 —— tat_ns 必须单调不减，一旦被拨回，之后整个桶的状态全错，且不会有任何报错。

至于 oversize，精简版与完整版行为相同（都按实际 cost 计费、自动延长等待、绝不截断，见 4.1），只是不再打 warning。

// 由 tokens = B - (tat - now)*R 反解
tat_ns = real'($realtime) + tok2ns(cfg.bucket_size - init_tok);
  • init_tokens < 0 约定为「装满」，这样默认值 -1.0 就表示满桶；想测稳态则显式写 0.0
  • 超过桶深的初值被裁剪 —— 桶装不下更多
  • 满桶 ⟹ tat_ns = now；空桶 ⟹ tat_ns = now + B/R，即「要等 B/R 才攒满」
  • 前置三道 fatal 检查：cfg 非空、rate > 0、bucket_size > 0。速率为 0 会让 tok2ns() 除零，必须挡在门外

7.3 tok2ns() 与 effective_cost()

protected function real tok2ns(real tok);
    return (tok / cfg.rate_tokens_per_sec) * 1e9;
endfunction

唯一的单位换算点。1e9 这个常数意味着整个类假定 timeunit = 1ns，改 timescale 必须同步改这里（已列入已知限制）。

effective_cost() 做三件事：

  1. cost <= 0 直接归零 —— 零开销的包不占额度，也避免负数把 TAT 往回拽
  2. cost > bucket_size 时按 allow_oversize 分流：1 则 warning 后放行，0 则 fatal
  3. 无论如何返回原值，不截断。这是 4.1 讲的那条：截断等于给大包打折，长期速率会超标

7.4 consume() 逐段解读

这是全类的核心，分四段。

第 1 段 — 进门记账

t_enter = $realtime;              // 用于算本次调用的阻塞时长
need    = effective_cost(cost);   // 校验在锁外做, 不占临界区

第 2 段 — 锁内 O(1) 预约时隙

sem.get(1);
t_ns        = real'($realtime);
earliest_ns = tat_ns - tok2ns(cfg.bucket_size - need);
start_ns    = (earliest_ns > t_ns) ? earliest_ns : t_ns;
tat_ns      = ((start_ns > tat_ns) ? start_ns : tat_ns) + tok2ns(need);
sem.put(1);
行含义
earliest_ns「令牌够了」的最早时刻，由 tokens ≥ need ⟺ t ≥ TAT − (B−need)/R 直接得出
start_ns实际放行时刻 = max(最早时刻, 当前时刻)。令牌已够时取当前时刻，立即放行
tat_ns 更新先 max(start_ns, tat_ns) 再加 need/R。内层 max 保证空闲期不会让 TAT 落后于现在（否则桶会「攒出」超过 B 的额度），外层加法就是把这个包的额度从未来扣掉

这四行不消耗仿真时间，所以临界区是真正的 O(1)，不存在队头阻塞。多条流并发时按到达顺序各自拿到一个互不重叠的时隙 —— 这正是 tc_buck_shared 能让总带宽受限的原因。

第 3 段 — 锁外等待

delay_ns = start_ns - t_ns;
stalled  = (delay_ns > 0.0);
if (stalled) #(delay_ns * 1ns);

一次闭式延时，没有循环逼近，也不需要「防零延时死循环」的兜底判断。stalled 这个标志随后用来界定稳态起点。

第 4 段 — 出门记账

if (grant_cnt == 0) begin first_grant = $realtime; last_grant = $realtime; end
if ($realtime > last_grant) last_grant = $realtime;
grant_cnt++;
total_stall += ($realtime - t_enter);
account(need);

if (stalled && !steady_valid) begin   // 首次 stall ⟹ 突发信用耗尽
    steady_valid = 1;
    steady_start_time = $realtime;
    steady_start_cost = total_cost;
    steady_start_cnt  = grant_cnt;
end
  • last_grant 用 max 更新而非直接赋值：并发时多个进程可能在同一时刻完成，顺序不定，直接赋值会把窗口右端往回拨
  • 这一段全是非阻塞运算，天然原子，所以刻意不持锁
  • 「首次 stall 即稳态起点」是一个干净的判据：桶里还有存货时不会 stall，一旦 stall 说明存货已空，此后系统完全由 R 支配

7.5 account()：O(1) 覆盖任意窗口的符合性

span_s   = (last_grant - first_grant) / 1e9;
f_before = total_cost - span_s * cfg.rate_tokens_per_sec;
if (f_before < f_min) f_min = f_before;      // running 最小值

total_cost += add_cost;

f_after = total_cost - span_s * cfg.rate_tokens_per_sec;
if ((f_after - f_min) > max_excess) max_excess = f_after - f_min;

原理见 4.2：令 f(t) = cost(t) − R·t，任意窗口 [t₁,t₂] 的超额就是 f(t₂) − f(t₁)，其最大值等于 f(t) − min f。所以只要维护 f 的 running 最小值，就能用一次比较覆盖所有窗口，不需要存历史。

注意加 cost 前后各算一次 f：加之前的值用来更新 f_min（窗口左端应取在本包之前），加之后的值用来更新 max_excess（窗口右端取在本包之后）。顺序颠倒会让同一个包既算进左端又算进右端，低估超额。

7.6 try_consume()：非阻塞版

逻辑与 consume() 的第 2 段相同，差别只有两点：

  • earliest_ns > t_ns 时立即返回 0，不推进 tat_ns —— 没放行就不该扣额度
  • 不取 sem。整个函数是 function（不消耗仿真时间），在 SV 调度里天然原子

统计口径与 consume() 对齐：同样走 account()、同样更新 first/last_grant 与 grant_cnt，所以两种调用方式可以混用而不破坏报告。唯一不记的是 total_stall（它从不阻塞）与稳态起点（它从不 stall）。

7.7 current_tokens()：可以为负

tok = cfg.bucket_size - (tat_ns - real'($realtime)) * cfg.rate_tokens_per_sec / 1e9;
return (tok > cfg.bucket_size) ? cfg.bucket_size : tok;

上限裁到 B（桶装不下更多），但不裁下限。负值是有意义的：oversize 的包借支了未来额度，TAT 被推到很远，此时令牌数为负正确反映了「欠账」状态。这个函数只用于 UVM_DEBUG 日志，不参与任何判定。

7.10 使用约束小结

  1. 先 configure() 再用。它同时负责参数校验与统计清零，漏调会用到未初始化的 tat_ns
  2. consume() 是 task，必须在 task 上下文里调。需要非阻塞语义时用 try_consume()
  3. 自愿 idle 不违约。契约 cost ≤ R·T + B 是单侧不等式，只管「不许更快」。实际速率 = min(桶上界, 请求到达速率)，想让桶成为瓶颈需保证请求足够密
  4. idle 要插在 finish_item() 之后，不要插在 consume() 之前 —— 后者会把自愿等待计入 total_stall，污染稳态起点的判定
  5. timeunit 必须是 1ns，见 7.3

8. 流量统计原理

这一章先把第二部分的方法论讲清楚：手上只有一串「某时刻走过多少字节」的记录，凭什么能把当初配进桶里的 R 和 B 原封不动地算回来。后面 §10 讲这套方法怎么用队列实现，§11 讲怎么拟合，本章只管「为什么是这套方法」。

8.1 观测与产生是一对逆问题

两条分支做的是同一件事的两个方向。第一部分已知 R / B，要算出每个包该在什么时刻放行；第二部分已知每个包实际在什么时刻走过，要反算 R / B。

第一部分：令牌桶第二部分：滑窗统计
已知R、B、包长序列到达时刻序列、包长序列
求解每个包的放行时刻R、B
方向参数 → 波形（正问题）波形 → 参数（逆问题）
手段GCRA 虚拟时间递推（§3）滑窗峰值包络 + 最小二乘（§10、§11）
出错表现发出的流量超速反推值与配置值不符

正问题只有一个解，逆问题却天然带误差 —— 这是第二部分一切容差、拟合、离群判定的根源。逆问题能解出来的前提是「激励足够丰富」：桶若一直闲着没把信用用光，观测数据里就不含 B 的信息，再好的算法也反推不出桶深（这正是 exp_B 的上界比对只在 burst case 才有分辨力的原因，见 §12.3）。

8.2 包络函数：流量的完整画像

要把一条流量描述清楚，一个数字不够。定义峰值包络函数：

peak(W) = maxt { 时间窗口 (t−W, t] 内走过的字节数 }

它是「窗口宽度 W」到「该宽度下最坏情况字节数」的映射。令牌桶契约 cost ≤ R·T + B 要求对任意窗口成立，翻译成包络函数就是一条上界直线：

peak(W) ≤ R·W + B　（对所有 W > 0）

于是整形参数就藏在这条曲线的几何形状里：

几何量物理含义由谁度量
W → ∞ 的斜率长期速率 R宽窗口
W → 0 的截距突发额度 B窄窗口
曲线是否穿过上界整形器是否违约所有窗口

平均速率只是这条曲线在 W → ∞ 处的渐近斜率 —— 它丢掉了截距，这就是 §9 要演示的盲区。

8.3 为什么必须多档窗口

只测一个窗口宽度，得到的是曲线上一个点。一个点定不出一条直线 —— 两个未知数至少要两个方程。更关键的是，单点在数值上还是病态的：

只测这一档peak(W) 的构成后果
窗口极窄B 占主导，R·W 几乎为 0测得出 B，但 R 无从分辨
窗口极宽R·W 占主导，B 被淹没测得出 R，B 的相对权重趋于 0
只测中间一档两项混在一起一个方程两个未知数，无解

所以组件在 [win_min_us, win_max_us] 之间取 win_num 档（§13.1），在一次仿真里同时维护这么多个滑窗，拿到的是曲线上一串点，再用最小二乘同时解出斜率与截距。

档位该怎么排：等比而非等差

有了多档之后还有一个容易被忽略的问题：这些档位在区间里怎么分布。直觉上等差最自然，但它对这个拟合问题是错的。两个理由：

① 截距靠最窄端的点支撑。B 是直线外推回 W = 0 的截距，最窄一档离 0 多远、窄端的点有多密，直接决定 fit_B 的方差。等差分段在对数轴上是头重脚轻的 —— 以 125/250/…/1000us 为例，8 个点里有 4 个挤在 500~1000us 这半个区间，而窄端只有 125us 孤零零一个点，截距全靠它从 125us 外推回 0，杠杆臂长、误差被放大。

② 拐点位置本身就跨数量级。曲线的拐点在 W* = B / R（桶被灌满所需的时间），拐点之前截距主导、之后斜率主导，两边都要有点才解得准。而 W* 随配置变化极大，本工程六个 case 分别是：

caseR (byte/us)B (byte)拐点 W* = B/R
tc_buck_base / beatgap10.01024102 us
tc_buck_pps6.41024160 us
tc_buck_shared4.01024256 us
tc_buck_rate1.0512512 us

跨了 40 倍。任何一个固定的窄区间都不可能同时覆盖 —— 老的 125~1000us 对 burst 来说全部落在拐点之前（拐点 4096us 比最宽档还远 4 倍），那个 case 的斜率只能靠曲线上 21% 的变化量去撑。要让一套默认配置对所有 case 都够用，档位必须横跨多个量级，而在跨量级的区间里均匀布点就意味着等比。

等比：Wi = Wmin · (Wmax / Wmin)(i−1)/(N−1)　　i = 1 … N

默认取 10us ~ 10000us 共 8 档，即 10 / 27 / 72 / 193 / 518 / 1389 / 3728 / 10000 us，跨三个数量级。两端放宽是安全的：过窄的档会被 peak_depth > 1 滤掉，过宽的档会被 W ≤ 采样跨度 滤掉（§11.1），等于让组件自己从一个足够大的候选集里挑出有信息量的那几档。这也是为什么实测的参与拟合点数不再是固定 8，而是随 case 在 5~7 之间浮动。

实测效果（同一套激励，仅改分段方式）：最大误差从 2.58% 降到 1.04%，减半。改善最大的是 tc_buck_rate，fit_R 从 −2.58% 收到 −0.13% —— 它原先正是最差的一个，因为拐点 512us 落在老区间的中段，等差的点大半压在拐点之后。同时 fit_B 普遍更贴近真实桶深（base 的桶深利用率从 91% 升到 98%），窄端有了点之后截距不再靠长臂外推。完整对照见 §18。

等比与等差怎么选：固定用等比

win_log = 0 可退回等差分段（§13.1），但这不是一个需要你按场景去权衡的选项 —— 等差只是在「区间窄到一个量级以内」这个前提下才成立的特例，而那个前提恰恰不成立。

关键在于分段方式与区间宽度是绑死的。把默认区间 [10, 10000] 改成等差 8 档，步长是 (10000 − 10) / 7 ≈ 1427us，档位变成 10 / 1437 / 2864 / … / 10000。而上表六个 case 的拐点是 102 / 160 / 256 / 512 / 4096us —— 前四个 case 的拐点全部落进第一档与第二档之间的那段空白里，拐点前只剩 10us 孤零零一个点，还很可能被 peak_depth > 1 滤掉。区间一旦跨量级，等差就自动失效。

反过来，等差要有意义就必须把区间收窄到一个量级以内（比如旧的 125~1000us）。但凭什么收到那里？收窄的前提是事先知道拐点在哪，而拐点 = B / R —— 这正是待拟合的那两个未知数。

这就是整件事的闭环：拟合的前提是 R、B 未知；既然未知，就没有依据去挑那个窄区间；挑不了窄区间，就只能跨量级；跨了量级，就只能等比。

所以 win_log 是一个兼容开关，不是调优旋钮。它剩下的用途只有两个：

场景怎么配
常规验证，R / B 待反推等比 —— 默认值，不用配
已知 R / B，想在某个可疑宽度附近精查曲线形状直接给 win_us 显式列表，比切等差更准
复现旧回归基线做数据比对win_log = 0

注意第二行：真要做局部精细化，正解是 win_us 而不是等差。给了 win_us，上面四个自动分段参数全部被忽略（§13.1），档位想怎么排就怎么排，不必迁就等差那种均匀步长。

8.4 次可加但不保证凹

理论上的包络函数有一条好性质 —— 次可加性：

peak(W1 + W2) ≤ peak(W1) + peak(W2)

理由很直接：长度 W₁+W₂ 的最坏窗口总可以切成两段，每段的字节数各自不会超过对应宽度的峰值。这条性质保证了曲线不会「越长越陡」，也就保证了用直线去拟合是合理的。

但对离散包流，次可加成立、凹性不成立。包是一次性整块到达的，窗口边界扫过一个包时 peak(W) 会出现台阶式跳变，差分序列并不单调。源码注释里明确记了这一点 —— 所以组件不做凹性检查，只做残差离群（§12.1）与契约比对（§12.2）。拿凹性当判据会在包长波动的 case 上大面积误报。

与此相对，有一个量是严格稳定的：每档窗口的平均速率恒等于全局平均，与 W 完全无关（证明见 §10.4）。因此 peak / avg 的比值可以直接当作突发程度读：比值趋近 1 说明流量平坦，比值大说明存在集中突发。

8.5 四步流水线

整个第二部分就是下面四步，各步的详细实现分散在后续章节：

队列天然按时刻升序（monitor 按仿真时间顺序 write），所以要淘汰的一定在队头，不必遍历中间。每个事件一生只入队一次、出队一次，N 次 add() 总共最多 N 次 pop → 均摊 O(1)。

区间是半开的，所以判定写 t_q[0] <= lo —— 恰好等于 lo 的事件要被弹出。若写成 <，实际宽度变成 W+ε，相邻窗口会重复计入边界事件。

10.3 为什么只看到达时刻就够

把 S(t)（窗口内字节合计）完整画出来：

台阶只在两种时刻变化：在到达时刻上跳（新字节进入），在到达时刻 + W 下跳（老字节滑出左界）。

关键推论：两个相邻到达时刻之间没有新字节进入，而左界持续右移只会往外挤 —— 所以 S(t) 在这段区间内单调不增，极大值必然落在某个到达时刻的右端点上。

候选从「连续无穷多个 t」塌缩成「N 个到达时刻」。这是整个算法成立的前提 —— 否则求任意窗口的最大值是个无法穷举的问题。

10.4 每档窗口的平均速率恒等于全局平均

把窗口右端点在整个跨度上滑一遍求积分，每个事件被宽度 W 的窗口覆盖，贡献 nbytes_i · W：

∫ S(t) dt = Σ nbytesi · W = total_bytes · W
mean_rate = (total_bytes · W / span) / W = total_bytes / span

W 被约掉了。所以不管窗口取 10us 还是 10000us，窗口内的平均速率一律等于全局平均 —— 平均值这个统计量对窗口宽度完全不敏感，这也是组件只提供一个 avg_Bps() 的原因。

11.2 最小二乘拟合：从实测曲线反推 R 与 B

上面的「相邻差」是手算。组件在 report_phase 里用最小二乘自动完成这件事（fit_line()）：对所有有效点拟合 peak(W) = R·W + B，斜率落在 fit_R、截距落在 fit_B。

R = (n·Σ W·y − Σ W·Σ y) / (n·Σ W² − (Σ W)²)

B = (Σ y − R·Σ W) / n　　其中 y = peak_bytes，W 取 us

参与拟合的点与 hide_noise 的筛选条件一致：peak_depth > 1 且 W <= span。不足两点则跳过 —— 单点无法分离斜率与截距（一个方程两个未知数）。

12.2 契约比对（check_contract）

uvm_config_db #(real)::set(this, "env.win_stats", "exp_tol", 0.05);    // 5%

两项的判定方向不一样，这来自它们在契约里的角色不同：

项判定理由
exp_R双侧 |err| > tol 就报R 是要被「打准」的目标值。偏高是漏速；偏低同样是 bug 信号 —— 说明整形器发不出配置的速率，或激励不够密没把桶压满，两者都需要人看一眼
exp_B单侧 只有 err > +tol 才报B 是契约里的上界，不是目标值。契约 cost ≤ R·T + B 只说「突发不许超过 B」，没说「必须用满 B」

fit_B 比 exp_B 小是合法的 —— 它量的是「实际发生过的最大突发」，激励没把信用攒满时它自然偏小，曲线只是贴在上界下方，并未违约。fit_B 超出 exp_B 才是真问题：实际突发比桶深还大，说明整形器漏了。

这与 §12.1 的残差只判正偏差完全同源 —— 两道检查都只管「不许更快」，这正是令牌桶契约的单侧性质。

UVM_WARNING ... shaper profile deviates from contract (1 item(s)): R: fit = 1.7021, expect = 2.0000 byte/us, err = -14.90% (tol 5.00%) the fitted line is in the wrong place -- check the rate/depth actually programmed into the DUT against the expected values

exp_B 超限时的报文则写成上界形式，与判定方向一致：

B: fit = 9071.0, expect <= 8192.0 byte, over by +10.73% (tol 5.00%)

但在这些 case 上配 exp_B 几乎没有检出力：实测值离上界还差一个数量级，整形器得漏到 20 倍以上才会触发，而那种程度的漏速 exp_R 早就报了。只有 tc_buck_burst（以及顺带把桶用满的 tc_buck_base）把突发信用真正用光，fit_B 贴着上界，此时上界判定才是一道紧的检查 —— 桶深多给一点点就能抓到。

所以这里的取舍不是「怕误报」，而是把检查放在它有分辨力的地方。桶深是否被突破另有 is_conformant() 在桶内部逐包把关，不需要契约比对代劳。

第二行好理解：所有点一起抬高或压低，残差仍是零，只有拿绝对值比对才看得出来。第三行反直觉 —— 明明是「某个点偏离了直线」，残差法为什么会漏？

最小二乘的崩溃点。离群点会同时干两件事：把拟合线拽向自己，又把 sigma 撑大。两头一夹，它把自己遮住了（masking）。拿下面那组低端异常数据实算：8 个点拟合得 R = 8.887（真值 10）、B = 1885（真值 1024），最大残差 504.2 byte 折算只有 1.61 sigma，离 chk_sigma = 3.0 还远。把门限降到 1.5 虽能触发，但正常用例会满屏误报。

这里曾经有过第三道「凹性检查」，已经移除。当时的想法是：既然 peak(W) <= R·W + B，那各档应当呈凹形（相邻斜率单调不增），斜率一旦回升就报，还不需要任何外部参数。对上面这组数据它确实报得又准又直接。

但前提是错的。peak(W) 对离散包流只保证次可加（E(W₁+W₂) <= E(W₁) + E(W₂)），并不保证凹 —— 凹的是它的上包络 R·W + B 这条线本身。窗口边界扫过一个包时 peak 会整包跳一级，没扫到则持平，于是局部斜率必然在 0 与「整包 / 步长」之间抖动，噪声底就是一个包长。实测 tc_buck_burst（平均包长 140.7 byte、步长 125 us）相邻斜率为 1.352 / 3.48 / 1.888 / 1.64 / 1.28 / 1.576 / 3.32，围着真值 2.0 抖 ±1.1 byte/us ≈ ±137 byte，恰好一个包 —— 而这条流八档全在上界以下、conformant = YES，是完全合规的。

门限救不回来：tol = 0.05 折算 12.5 byte，不到一个包的 1/9，必然误报；放大到能盖住包长则需 4 byte/us 以上，比真值 R 还大，上面那组真实异常也一并放过。能滤掉噪声时就已经滤掉了信号。这类单档形变交给契约比对即可。

14.2 时序约定

  1. 每个 beat 在 valid && ready 同时为高的时钟沿被接收
  2. last 界定包边界
  3. 实际字节数 = Σ popcount(keep) over all beats
┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ clk ───┘ └──┘ └──┘ └──┘ └──┘ └──┘ └── ┌─────────────────────────┐ valid ───┘ └────────── ─────────┐ ┌─────────────────────── ready └─────┘ ← 背压 2 拍 ┌─────┬─────────┬─────┬─────┐ data ───┤ D0 │ D1 │ D2 │ D3 ├──────── └─────┴─────────┴─────┴─────┘ keep 1111 1111 1111 0011 ← 末 beat 仅 2 字节 ┌─────┐ last ───────────────────────────┘ └────── 此包 len = 4+4+4+2 = 14 字节，4 个 beat

令牌在整包第一个 beat 之前一次性扣除，不逐 beat 计费。否则大包会被拆散，bucket_size 将失去「允许多大突发」的语义。

14.3 DUT 行为 rtl/buck_sink.v

buck_sink 是一个带 FIFO 的接收端，每 DRAIN_PERIOD 拍排空一个包以模拟下游带宽上限。输出 pkt_cnt、beat_cnt、byte_cnt、fifo_level、drop_cnt、err_keep 供 monitor 自检。

14.4 包内 beat 空隙 env/buck_driver.sv

默认情况下一个包的各 beat 背靠背驱动。driver 提供钩子 beat_gap(tr, idx)，返回第 idx 个 beat 握手完成后插入的空闲拍数，基类返回 0，故已有 case 时序不变。buck_gap_driver 是一个现成的随机实现（见 tc_buck_beatgap）。

空隙只能插在握手完成之后。valid 一旦拉高，在 ready 到来前不得回撤 —— 这是 valid/ready 协议的硬性要求。因此实现上必须等 do...while(ready !== 1) 退出后再拉低 valid。末 beat 之后不插，包间节奏由令牌桶负责。

加入空隙后各层的受影响情况：

层次受影响原因
monitor / DUT 计数否二者都只在 valid && ready 成立时动作，空闲拍被天然忽略
符合性 is_conformant()否不依赖窗口口径，任何情形下严格成立
raw / steady 速率（§5）小空隙可忽略线速 4 B/2 ns = 2e9 B/s，base case R=1e7 仅占 0.5%，每 beat 平均还有约 400 拍裕量；超出后 driver 成为瓶颈，窗口分母被拉长，两项指标都会偏低
滑窗拟合（§11）间接包的到达时刻被推后，曲线整体右移、fit_R 略低；只要空隙远小于令牌间隔就在容差内（beatgap 实测 fit_R = 9.9922，偏 −0.08%）
背压 / FIFO 水位覆盖是见下

不要让每个 beat 都插空隙。本 demo 的 DUT 排空速率是 4 B/4 ns = 1e9 B/s，恰为线速一半。只有背靠背输入才能把 FIFO_DEPTH=16 填满并触发背压（36-beat 的包净积累 18 beat）。若每拍都插隙，输入降到排空速率以下，FIFO 永远填不满，背压路径与 driver 等 ready 的分支就都失去覆盖了。所以空隙必须是随机的、并保留相当比例的 0，让背靠背片段与空隙片段混合出现。

17. 如何自定义

17.1 改速率 / 桶深

继承 tc_buck_base，重载 set_bucket_cfg()：

class tc_my_case extends tc_buck_base;
    `uvm_component_utils(tc_my_case)

    function new(string name, uvm_component parent);
        super.new(name, parent);
    endfunction

    virtual function void set_bucket_cfg(token_bucket_cfg c);
        c.rate_tokens_per_sec = 5_000_000.0;  // 5 MB/s
        c.bucket_size         = 2048.0;
        c.init_tokens         = 0.0;          // 从空桶起，直接测稳态
    endfunction

    virtual function int unsigned get_num_items();
        return 500;
    endfunction
endclass

记得把新 case 加进 Makefile 的 TC_LIST 和 regress.csh。exp_R 由基类的 set_win_exp() 按 rate/1e6 自动跟随，无需另写；只有改了计费单位或要卡 exp_B 时才需重载（见 §12.3）。

17.2 从控带宽切换到控包率

重载 item_cost() 即可，速率单位随之改变：

// 控 byte/s（默认）
virtual function real item_cost(buck_transaction tr);
    return real'(tr.len);
endfunction

// 控 packet/s
virtual function real item_cost(buck_transaction tr);
    return 1.0;
endfunction

// 也可自定义加权，例如计入每包固定开销
virtual function real item_cost(buck_transaction tr);
    return real'(tr.len) + 24.0;   // 模拟前导码 + IFG
endfunction

改了 item_cost() 就必须同步改 set_win_exp()。滑窗统计量的永远是字节，而桶的令牌单位由 item_cost() 决定，两者口径一旦分叉，契约比对就会误报。tc_buck_pps 正是这种情况：令牌是「包」，故 exp_R 要乘定长包长 64。

17.3 加包长约束

virtual function void randomize_item(buck_transaction tr);
    if (!tr.randomize() with { len inside {[64:1518]}; })
        `uvm_error("RNDFAIL", "randomize failed")
endfunction

17.4 多流共享总带宽

把同一个 token_bucket 句柄交给多条 sequence，总流量即受统一限制（见 tc_buck_shared）：

fork

也可不显式赋值，由 sequence 自行从 uvm_config_db#(token_bucket) 按 bucket_name（默认 "tb_bucket"）获取。滑窗统计挂在 monitor 上，看到的是合流后的总流量，因此 exp_R 仍按桶的配置速率填即可。

17.5 加包内空隙

重载 beat_gap()，再用 factory 把 driver 换掉：

class my_gap_driver extends buck_driver;
    `uvm_component_utils(my_gap_driver)
    // ... new() ...

    virtual function int unsigned beat_gap(buck_transaction tr, int unsigned idx);
        if ($urandom_range(1, 100) > 40) return 0;   // 60% 背靠背
        return $urandom_range(1, 3);
    endfunction
endclass

// 在 test 的 build_phase 里, super.build_phase() 之前
buck_driver::type_id::set_type_override(my_gap_driver::get_type());

判据要跟着改。包内空隙会把单包搬运时间拉长，从而推后下一次 consume() 的调用时刻，这在墙钟窗口上表现为 raw / steady 偏低 —— 它们的分母无法区分「等令牌」与「等总线」。因此这类 case 不应以速率为判据，只卡符合性与协议/计数对账两件事（参见 tc_buck_beatgap）。另外切记保留相当比例的 0 空隙，否则背压覆盖会丢（见 §14.4）。

19. 已知限制

  • timescale 固定为 1ns/1ps。token_bucket 用 /1e9 把 $realtime 换算成秒，依赖 timeunit=1ns。修改 timescale 需同步调整该换算（见 §7.3）。
  • tc_buck_burst 未设 raw 误差门限。当前主判据是 steady + 符合性。若要卡 raw，门限应随窗口自适应（约 B/(R·T) + 2%），而非写死常数。
  • oversize 路径未被回归覆盖。当前 len ≤ 256 小于最小桶深 512，走不到该分支。需验证可加一个 bucket_size=128 的 case。
  • drop_cnt 统计的是背压拍数（valid && !ready），不是真正的丢包。
  • tc_buck_beatgap 的背压覆盖未经实测验证。monitor 的 summary 不打印 drop_cnt 与 fifo_level 峰值，因此「插隙后 60% 的 beat 仍背靠背、背压路径仍被打到」只是理论推断。要确认须在 buck_monitor.sv 的 report_phase 里补打这两个值。
  • $value$plusargs 须判返回值。plusarg 不存在时不可假定目标变量保持默认值，必须 if (...) n = arg; —— 此前因此踩过一次坑，num_items 被意外变成了上次扫描的残留值。
  • exp_B 只在 burst case 有分辨力。契约比对对 exp_B 是单侧上界判定，给任何 case 配上都不会误报；但滑窗拟合的截距量的是实际观测到的最大突发，空桶起步的 case 永远攒不满信用，实测值离上界差一个数量级，这道检查松得抓不住东西（见 §12.3）。要让 exp_B 普遍变紧，需要在 sequence 里安排一段显式的静默期把桶灌满。
  • 滑窗只在 report_phase 一次性分析。不做在线实时判定，因此无法在违规发生的那一刻停仿真。要定位具体时刻须查 win_fit.txt 里的残差明细（见 §13.4）。
